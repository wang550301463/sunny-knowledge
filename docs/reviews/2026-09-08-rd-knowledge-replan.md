# sunny-knowledge：研发知识平台评审与重规划建议

日期：2026-09-08。评审基线：`7bf0f36`。状态：供讨论的架构建议，尚未批准为新 schema，也不替代原设计规格。

用户已确认：首版优先研发知识，重点为代码、依赖、变更与故障追溯；来源包含 Java、TypeScript、Go，并希望有较高扩展性。本文不修改业务代码、正式结论或 AGENTS.md。

## 1. 判断与范围

方向可以保留，当前实现需要按“可演示原型”重新定位。最重要的缺口不在于少用了哪个模型，而在于证据、知识版本、索引、权限和自动写回之间没有形成可靠的约束。

建议产品定义：**一个以版本化 wiki 为知识主存、能够沿证据解释研发事实变化、通过统一 API / MCP 提供受控检索的知识平台。**

首个业务域选择少量互相依赖的真实仓库，加关联的变更、故障和运行手册。范围以可完成专家标注为准，暂按 1–3 个关联服务启动；真实仓库总量尚未确认。语言覆盖 Java / TypeScript / Go，先用一个跨语言业务链路验证。Go 是平台现有实现语言，不限制解析器的实现语言。

首版需要回答：

- 某服务依赖哪些组件？来自哪个仓库、分支、提交、文件？
- 某依赖升级可能影响哪些已知调用方？哪些路径只是推断？
- 某故障发生时使用什么版本？后来由哪个变更修复？
- 发布、回滚和排查流程是什么？流程当前是否仍有效？
- 这个回答依据什么，哪些部分缺证据？

“当前”必须区分默认分支状态与生产部署状态。没有部署记录时只能回答“仓库在提交 X 的声明”，不能推成“生产正在运行 X”。图未记录调用路径也不代表没有影响。

## 2. 现状中可以保留的部分

- wiki 优先，图用于导航与时序，原文用于精确引用的职责方向。
- Go 包结构中的 ingest / query / wiki / graph / evolve 边界。
- 已有实体与边类型、单一 `group_id=enterprise`、人审原则。
- 图故障时返回 wiki 的降级意图、失效历史保留意图。
- 左图右页的查看方式、现有演示语料和测试作为基本回归材料。

需要明确：原文是事实核验依据，已发布 wiki 是平台当前采用的解释。发现原文与 wiki 冲突时，应显示冲突并发起修订；既不让 chunk 静默覆盖 wiki，也不让过期 wiki 阻止发现新证据。

参考文章提供的是编译、生命周期、检索与协作的构想，不能替代本项目的数据契约、权限模型和验收结果。参考：[LLM Wiki v2](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2)。

## 3. 已确认的实现缺口

以下基于当前代码静态检查。严重程度按本项目对接企业数据与外部 MCP 的目标评估，不表示已经在线上发生过事故。

### P0：身份与知识泄露边界

`internal/httpapi/auth.go:18` 校验一个共享 X-Token，再直接信任调用者提交的 X-Role。任何持有该令牌的调用者都能自称 admin；不是无令牌即可绕过，但没有实现角色隔离。

`internal/wiki/search.go:47` 对 All() 返回的页面全量检索；`internal/httpapi/server.go:53` 的页面读取不核验 private 所有人；`internal/ingest/project.go:19` 投影所有页面。当前 private 是元数据和部分写入路径限制，不构成读取、检索或图投影隔离。

`internal/evolve/mesh.go:72` 的 Promote 忽略 actor；HTTP 层的 editor 限制不能证明该 editor 有权读取或公开别人的 private 页。晋升还按文件名落到 shared，可能撞名覆盖。

改造要求：服务端建立 principal；角色与 agent 身份来自已验证的认证信息；页面、证据、图节点和导出均按资源授权；查询前过滤、回源时再次校验。private 派生摘要不得变成 shared。首版共享图只接入经确认对试点用户共同可见的内容，私有来源不进入共享 Graphiti 抽取上下文。

### P0：无质量评估的自动结晶

`internal/httpapi/server.go:50` 每次 ask 都把 quality 固定传为 0.9，随后忽略写回错误。`internal/crystal/crystal.go:22` 覆盖同一个 digest-latest，并设 confidence=1。摘要又会被下一次搜索读到。

后果：无命中、降级、错误或过期回答也可能被视为合格知识，反复检索和写回形成自我强化。现有 0.7 阈值并未真正衡量质量。

改造要求：先实现可解释的质量门控和证据追踪；不合格结果不写入合格 digest。合格摘要保留不可变历史及原始证据链，最新页只是入口；衍生摘要不增加“独立证据数量”。正式结论的覆盖仍需人审。

### P1：混合检索与图遍历尚未接通

`internal/wiki/search.go:47` 每次读全库并计算词频与逆文档频率，没有 BM25 长度归一化，也没有向量索引。

`internal/query/ask.go:64` 融合的是 wiki 路径和关系文本，两种 ID 不对应同一候选对象；fused 结果仅用于空答案提示，未控制最终证据选择或排列。实际答复是前五页正文与图文本拼接。

`internal/query/ask.go:28` 未调用 Neighborhood。`internal/graph/http.go` 的 Neighborhood 只是搜索后附加一个中心节点，并非真实邻接遍历。

改造要求：建立增量索引；BM25、向量和图扩展都映射回统一的 wiki section / claim 候选 ID；融合后重排、回源和组装证据。关系题才执行有边类型、方向、时间与预算限制的遍历。

### P1：真实 Graphiti 适配不具备 Fake 的时序语义

`internal/graph/http.go` 的 Search 解码 valid_at / invalid_at 后未放进返回 Fact；将整句事实塞入 Source，并把 Kind 固定成 uses，Target 为空。Ask 再以 InvalidAt 是否为空判断“现行”。这会丢失后端已经提供的失效信息。

AddFact 和 Supersede 实际把自然语言送入 episode，不保证产生指定 ID 的边或准确失效指定事实。Fake 则是确定性地修改 map。现有 HTTP 测试主要检查向 /messages 发请求，两者并未通过同一组语义验收。

改造要求：锁定 Graphiti 发布版本 / commit，建立 SDK 适配服务和契约测试。保存本地稳定 ID 到外部 UUID 的映射，保留完整时态。提交 episode 的受理结果不等于投影完成。确定性依赖边与 LLM 推断关系分别标记来源；后者不能直接升级为正式依赖结论。

Graphiti 官方提供混合检索和时序能力，但平台仍须验证自己的适配与授权边界。参考：[官方仓库](https://github.com/getzep/graphiti)、[服务检索实现](https://github.com/getzep/graphiti/blob/main/server/graph_service/routers/retrieve.py)。

### P1：接入流程仍是样例脚本

- `internal/ingest/ticket.go:39` 将工单写成 pay-api uses redis-7，通过文本是否含 supersedes 决定失效 e-old。
- `cmd/ingest/main.go:42` 主动种入 redis-6；制度解析使用 docs.NewFake()。
- `internal/ingest/code.go` 主要复制 README、列文件、读取固定 docs/CHANGE.md；未提取实际依赖、代码结构与源位置。
- 多仓库共用 entities/files.md 和 procedures/change.md；制度固定 policy-refund.md，无法安全接入多个同类来源。

改造要求：来源独立命名空间、不可变 source revision、语言适配器、增量 diff、幂等作业。缺运行手册时记录缺口，不凭空编标准流程；工单中“计划升级”与“已完成升级”必须区分。

### P1：RAGFlow 尚未实现解析与逐字引用

`internal/docs/ragflow.go:23` 把文件字节发到创建 dataset 的路径后返回原始字节；Cite 始终报错。`internal/docs/wikicite.go` 返回编译后的正文，不能普遍作为原文逐字引用。

官方 API 区分创建 dataset、上传文档、触发解析和获取 chunk；HTTP 成功也需检查业务 code。来源：[RAGFlow HTTP API](https://ragflow.io/docs/http_api_reference)。

研发优先阶段先做 Git 固定提交的代码行引用与 Markdown 段落引用。PDF 接入独立安排，继续保持解析失败只留 raw、关闭 RAGFlow GraphRAG，不让 PDF 阻塞首个研发闭环。

### P1：发布、持久化与审计没有统一写入口

`internal/wiki/store.go:31` 直接覆盖文件，无版本比较、原子替换或事务。Ask 刷新访问时间、编译、工单和结晶都直接 Write，绕过 Mesh。Mesh 的锁与 mtime 仅在单进程内存，检查与写文件也不在同一临界区。

`internal/evolve/queue.go` 的审批只修改内存状态，没有关联可执行补丁、目标版本或持久化。当前审计调用主要在 cmd/lint，没有覆盖发布、自动失效、晋升和审批。

改造要求：全部写入统一经过 KnowledgeService。锁用于协调；版本比较和发布事务用于正确性。审计、审批决定、当前版本指针、投影事件需要一致提交。图 / 索引失败后可重试和对账，不能靠忽略错误维持表面成功。

### P2：衰减结果取决于定时任务执行次数

`internal/evolve/decay.go:68` 把已衰减 confidence 再乘以“从原强化时间至今”的完整衰减。固定 now 在一个半衰期之后，重复 Apply 两次会从 1 变 0.5 再变 0.25。

改造要求：从固定基值和固定时间原点计算，或记录上次衰减时刻只应用增量。相同 now 重跑必须幂等。访问仅更新 last_accessed；有效性、证据质量、热度和新鲜度应分开解释。是否调整字段与评分语义列入第 11 节人审建议。

## 4. 三种路线与推荐

### A. 延续文件脚本，逐个打补丁

最省迁移成本，适合个人本地实验；随着并发写入、权限、版本和任务恢复加入，文件周边会不断长出数据库功能。不建议作为企业目标架构。

### B. 保留 wiki 概念，增加可靠的知识控制面（推荐）

Go 模块化单体承载 API、MCP 和知识规则；后台 worker 处理编译与投影。版本化 wiki 保存正式内容，事务元数据保存发布指针、权限、审核和任务，搜索与图均可重建。

优点是复用现有方向，又能逐条验证工程不变量。代价是增加事务存储和迁移工作。先单业务域部署，不立刻拆大量微服务。

### C. 让 Graphiti 或 RAGFlow 直接成为主平台

集成初期可能较快，但会把版本、审批、wiki 优先和外部授权控制分散到组件行为中，与当前项目纪律冲突。Graphiti 已有 MCP，也不应因此直接绕过本平台对外暴露全部能力。

## 5. 推荐的职责划分与部署

**原始证据层**：Git commit / 文件快照、工单版本、部署记录、文档原文。保存来源 ID、revision、内容哈希、抓取时间、权限与精确位置。敏感原件与可供模型处理的脱敏副本隔离，模型只接触获准副本。

**知识主存层**：wiki 页面、页面修订、页面内有出处的声明及人工发布状态。正文保持 Markdown；页面与声明的修订可追溯、可回滚。结构化声明是页面的组成部分，不另造一个可独立改写正式结论的事实库。

**控制面元数据**：建议 PostgreSQL 管理来源清单、当前 wiki revision 指针、ACL、任务、审批、审计及 outbox。页面正文可存为不可变 Markdown blob，先可靠写入并校验，再在数据库事务中切换活动指针。未提交指针的 blob 不可见；投影只消费已发布修订。普通路径编辑进入提案导入，不再直接改活动版本。

**索引层**：建议试点使用一个 OpenSearch 承载 wiki section 的 BM25 和向量索引。中文描述、代码标识符、完整路径与版本号使用不同字段；分析器和 embedding 模型以真实查询测定。RRF 由 Go 编排，避免把搜索引擎内部融合结果再重复计票。OpenSearch 是可替换读模型，数据库仍管理发布与授权。

OpenSearch 官方支持关键词与语义混合检索及不同融合方式；这里选择它是减少检索后端数量的设计建议，不是经过本项目压测的结论。参考：[混合检索文档](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/)。

**图层**：Graphiti + Neo4j，仍使用 enterprise。通过小型 Python SDK 适配层提供受控操作，锁定版本。图提供候选关系、邻接路径和时态导航；路径回指本地 wiki revision / claim / source revision 才可支持正式答案。无可验证映射的 LLM 关系只作待核验线索。

**服务层**：REST、管理界面、MCP 共用 KnowledgeService / RetrievalService，避免各自实现一套规则。检索可独立返回结构化证据，内部 ask 生成答案为可选消费者。

**异步层**：初期数据库作业表 + outbox worker 足够。重试、租约、幂等键、失败队列和状态可查；没有现成基础设施需求时不先加 Kafka 或复杂工作流引擎。

首版先部署 Go API / worker、事务库与 wiki blob、搜索；图在检索基线之后接入。RAGFlow 在文档需求进入试点后补齐真实适配。所有新增基础设施均是待评估建议，不在本轮启动。

## 6. 索引 → 混合检索 + 图遍历如何真正协同

### 6.1 索引单位和统一标识

检索单位建议为 wiki section 或有独立证据的 claim，不能把整仓库、整本 PDF 或大页全文塞成一个检索项。

每项最少关联：stable ID、page ID、page revision、source revision、entity IDs、文本、出处、ACL、发布时间、适用分支 / 环境、生命周期状态。业务实体仍用现有十类；SourceRevision、Job、Review 等只是管理记录。

实体 ID 按来源命名空间生成，不能以 module 最后一段或文件 basename 作为全局身份。例如 File 用 repo ID + path，具体内容再绑定 commit；同名模块不自动合并，别名通过审核挂接。

### 6.2 在线查询流水线

1. **确定范围**：认证 principal，解析 repo、branch、environment、as_of；缺部署数据时标明适用范围。
2. **并行召回**：BM25 捕捉精确术语 / 路径 / 错误码，向量捕捉语义表述；在可见的已发布 wiki section 上检索。目录与人工索引页继续用于导航，不再承担全量搜索。
3. **首轮融合**：两路使用相同候选 ID，按名次进行加权 RRF，去重后取种子。初始每路 top 40、融合 top 20，只是调试起点。
4. **实体链接与有界扩展**：从问题的明确实体与种子页面找中心；按问题选边类型和方向。依赖影响题沿 depends_on / uses 的反向边，先一跳，证据不足再二跳。设最大节点、最大边、时间和候选预算，防止高度连接节点淹没结果。
5. **图回流**：把图找到的实体和路径映射回支撑它们的 wiki section / claim，加入候选并补齐路径证据。保留“由什么种子、沿什么边发现”的信息，不直接把一句 graph fact 当 wiki ID 融合。
6. **重排和约束**：评估与问题的相关性、出处、有效期和重复度。ACL、正式发布状态、时间有效性是硬过滤，不能靠权重“压下去”。同一原始证据不能因页面、图和摘要重复出现而多算独立支持。
7. **回源验证**：核对当前 revision 与授权，获取 wiki 正文和必要原文片段。图落后时剔除不再有效的关系；不足以回答影响题时返回部分结果与不完整原因。
8. **输出证据包**：返回结论或候选、页与原文引用、关系路径、时间范围、未解决冲突、降级状态。可选生成器只根据该证据包组织语言。

加权 RRF 的形式是 `Σ weight[channel] / (k + rank[channel, candidate])`。可先设 BM25=1、向量=1、图扩展=0.5、k=60；这些都是待评测参数。wiki 与图的权威关系由回源验证保证，不由一个分数保证。逐字引用的原文 chunk 是证据附件，不与编译结论争夺发布权。

### 6.3 查询例子

以下为设计示例，未声称真实仓库存在这些事实：

“升级 Redis 后，退款链路可能影响哪些服务？”

- 词法与语义检索找到缓存使用说明、依赖声明和变更记录。
- 将 Redis、退款模块和关联服务链接到稳定实体。
- 反向遍历 uses / depends_on，收集调用方及每条边的证据。
- 关联 Change / Incident 的有效时间，排除已被取代的关系。
- 返回可证实的影响路径和对应 commit / 工单；未观测的动态调用列为覆盖不足。

普通“发版流程是什么”查询可以只用 wiki；“上月事故时的配置”要加历史版本和时间过滤。图扩展只在能增加必要证据时参与。

### 6.4 时间语义

至少区分事实在业务上有效的时间与平台何时获知该事实。业务时间条件为 `valid_from <= as_of < valid_to`，无 valid_to 表示未声明结束；若查询“当时我们知道什么”，再约束 recorded_at。

迟到工单不能用抓取时间覆盖其实际生效时间。“计划升级”“测试分支升级”“生产完成升级”不能合并成一个当前事实。supersedes 必须指向确定的旧声明并附依据，不能靠关键词触发。

## 7. 增量编译与发布闭环

建议状态：发现来源 → 抓取不可变版本 → 确定性解析 → 生成编译提案 → 验证 / 必要审核 → 发布 wiki revision → 投影索引与图 → 对账完成。失败记录当前阶段、错误和重试次数。

- 来源：Git webhook 加周期对账；初期手动触发同样走统一作业入口。
- 幂等键：source ID + source revision + compiler version + schema version。重复投递不重复写入和计费。
- 代码事实：优先构建文件、锁文件、AST、静态引用和已有配置；语言适配器声明自己的覆盖范围。动态配置、反射或外部运行态缺失时不声称全量调用图。
- 语义编译：LLM 负责归纳用途、解释流程和提出关系；每个可核验声明要求源位置。没有依据的推断保持候选状态。
- 工单：抽取所涉服务、变更动作、完成状态、时间和证据；复盘根因属于正式结论时进入审核。
- 更新：源 diff 只重新编译依赖这些源位置的页面；维护反向依赖清单，编译器升级可以按版本重建。
- 删除 / 撤权：先在服务读取边界阻止继续使用，产生索引和图撤回任务；保留受控历史和审计，不再默认召回为现行。
- 图重建：确定性投影可比较 ID 和版本清单；LLM 抽取结果须版本化保存，重放同一结果用于恢复。重新运行 LLM 是新的提案，不能假设输出完全相同。

发布事务中记录 wiki revision 指针、审批结果、审计事件和 outbox。搜索与图最终一致，通过 projection_status、projected_revision、last_error 观测。事件重试必须检查 revision，旧事件不得覆盖新投影。只有日志里出现“成功”不算完成。

### 7.1 Java / TypeScript / Go 的扩展接口

扩展点建议只有四类，不先做复杂插件市场：SourceConnector 负责抓取和 revision；LanguageAnalyzer 负责确定性代码分析；KnowledgeCompiler 负责把标准分析结果编译为 wiki 提案；ProjectionAdapter 负责投影到搜索和图。每类有版本化输入输出、超时、能力声明和契约样例。

LanguageAnalyzer 的统一输入为 source snapshot、repo ID、revision、子目录和分析配置；输出为模块清单、文件、符号、依赖、引用关系、配置、证据位置、未解析项和诊断。每条结果必须包含来源位置、分析器版本及确定性 / 推断标识。这里的符号等是分析中间表示，并不直接新增业务本体类型；编译时映射到既有 Module / File / Dependency 及边。

- Java：从 pom.xml / Gradle 声明识别模块与依赖，再解析包、类型和方法。依赖声明与最终解析版本分开；无法获得有效构建模型时明确标注未解析。Spring Bean、RPC、ORM 等作为框架分析规则逐批加入，不让通用 AST 直接声称理解全部运行态关系。
- TypeScript：识别 package.json、lockfile、workspace、tsconfig，再分析 import/export 与符号。区分 monorepo workspace、path alias、构建产物和源码；动态 import 和外部服务调用缺失时记录限制。
- Go：识别 go.mod / go.sum / go.work，保留 module / package 层级、文件与符号、import 关系及构建约束。依赖版本、replace 指令、build tag 与分析配置绑定。

三种语言共用来源身份、版本、证据位置和关系语义；检索与 MCP 不接触具体语法树。框架识别只增加分析能力，不复制整套 ingest。解析器可用各语言生态工具以隔离 worker / 子进程运行，Go 调用版本化 JSON 协议，不强制把 Java / TS 解析逻辑重写成 Go。具体解析器库在实施时核验官方维护状态与目标语言版本。

默认静态分析不执行来源仓库的安装、构建或测试脚本。确实需要依赖解析 / 构建信息时，使用显式配置的隔离任务、受控凭证和网络策略。无法解析的文件仍保留原始证据，但不能生成“分析成功”的伪关系。

扩展性验收：为三个语言各准备一个小型真实模块契约样例；接入第二种语言只增加 analyzer / framework 规则和配置，不修改 KnowledgeService、检索融合或 MCP 输出协议。一个多模块仓库、两个同名模块和一个跨语言依赖链必须纳入回归。

## 8. 自我进化应当进化什么

先自动维护可验证的变化，再引入有门控的内容提升：

1. 源变动使受影响声明标为待更新；明确完成的工单可按既有规则使旧声明失效并审计。
2. 检测缺引用、坏链接、来源撤回、长期未复核、查询无答案与用户纠错，形成维护任务。
3. 生成修订 diff，展示新旧正文、影响页面和来源；人工审批正式结论变更。
4. 离线评测新版本，再灰度发布；指标退化时回滚页面、编译器或检索配置。
5. 经过上述闭环后，才扩大自动合并低风险维护提案的范围。

质量 >= 0.7 的合格摘要仍写 digest-latest 并遵守现有 confidence / last_reinforced 规则，但必须先有真实质量评估。评估至少包含来源完整、关键结论受证据支持、无未解释矛盾、权限继承和非重复性；模型自评分只能作为信号。无证据、权限不明、关键投影缺失导致答案不完整时，门控直接不通过。

保留 digest 历史，避免 latest 丢失原回答；每个摘要记录 query ID、原始 source revisions、编译 / 模型版本与评估依据。仅重复自己的摘要不得触发强化。对“quality=1”或“confidence=1”的含义需要审定，不能把它解释成数学上的确定为真。

建议把 relevance（相关）、freshness（近期性）、support（证据支持）、status（是否有效）、authority（是否批准）分开。访问日志维护 last_accessed，不自动把“有人读过”解释为“又被独立证实”。衰减只用于排序与复核优先级，不能将一条仍有效的正式决策变成错误事实。

## 9. MCP 与管理产品

### 9.1 先暴露小而稳定的能力

- `knowledge_search(query, filters, limit)`：混合检索，返回候选、出处、版本、发现路径和降级信息。
- `knowledge_get(id, revision)`：读取可授权的 wiki / 证据对象；使用服务端 ID，不接受任意文件路径。
- `knowledge_traverse(entity_id, relations, direction, as_of, budget)`：受控图遍历，返回有来源的路径和覆盖限制。
- `knowledge_timeline(entity_id, from, to)`：事实与变更时间线；注明业务时间和获知时间。
- `knowledge_feedback(answer_id, reason, evidence_refs)`：写入纠错提案，不直接覆盖正式知识；独立写权限与审计。

`knowledge_ask` 可后加；外部 Agent 可以自行组织回答，平台优先保证证据获取可靠。MCP 与管理界面使用同一授权和查询服务，不能直接代理 Graphiti 的全部写入 / 删除工具。

远程交付建议采用 Streamable HTTP；本地联调可用 stdio。HTTP 认证授权按照目标客户端支持的 MCP 规范版本实现，包含令牌受众、scope 和资源检查；逐客户端服务身份不能由参数中的 actor 或 role 自称。参考：[MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)、[MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)。

每个响应约定 request_id、结构化结果、citations、as_of、revision、projection status、partial / warnings 和分页游标。引用支持重新打开同一版本。敏感数据不进入未授权 LLM / reranker、共享缓存或摘要；缓存键包含访问主体 / 权限版本与知识版本，撤权后旧缓存不可继续命中。来源内容作为不可信数据，不能让检索到的文本改变工具权限。

这里的“外部使用”暂理解为其他获授权的工具 / Agent 调用，仍是内部单租户企业服务，不预设开放互联网或多租户 SaaS。

### 9.2 管理界面围绕维护任务组织

- 接入：来源、同步分支、适用环境、权限、最近成功 revision、失败阶段和重试。
- 知识：正文、版本差异、源位置、维护人、有效期、待更新原因。
- 审核：待变更内容、新旧依据、受影响对象、批准 / 驳回及执行结果。
- 检索诊断：哪路找到证据、为何保留或过滤、引用能否打开。
- 质量：无答案、过期误答、用户纠错、索引延迟与编译成本。

图作为页面的关系查看工具，保留左图右页。企业管理的首页优先展示来源与维护事项，避免把全公司大图当成主要管理入口。

## 10. 按验收门槛推进的路线图

这些是阶段工作包，不是已批准的逐文件实现计划。每阶段应单独形成短规格、测试用例和可回滚交付；不按“模块名已存在”判断完成。

### P0：把演示边界和信任边界修好

涉及现有 httpapi/auth、wiki/store、query、crystal、evolve。

- 去掉调用者自报角色作为授权依据；补 private 读取、检索、引用和晋升校验。
- 把硬编码样例隔离到 demo fixture；无真实评估时不把回答判为合格摘要。
- 统一写入口、审计关键写操作、持久化审核；修复衰减重复执行问题。
- 增补 negative tests：reader 自报 admin、跨 agent private 读取、private 摘要公开、重复衰减、空回答结晶。

验收：这些已知失效场景全部被拒绝或正确处理；重启不丢审核；原切片演示仍可明确以 demo 模式运行。

### P1：真实来源 → 可追溯 wiki → 词法检索

复用 ingest/wiki 的包边界，新增 source、compiler、knowledge、jobs 管理模块；定义统一分析中间表示，Java / TypeScript / Go 先具备模块、文件、声明依赖与出处的基础适配，再按试点主语言补深度符号 / 框架分析。

- 导入固定 Git revision、关联运行手册及少量真实工单；剥离固定 pay-api / refund 路径。
- 页面与源版本、精确位置绑定；增量、幂等、发布和回滚可验证。
- 持久化 BM25 索引与统一 section ID，先建立可靠的词法基线。
- 管理面能够查看来源状态、失败重试、版本和引用。

验收：重复 ingest 不产生重复知识；两个同名文件 / 同名服务不互相覆盖；源变更只影响关联页；引用可打开原提交；任务中断后可恢复。

### P2：混合检索 + 只读 MCP

新增 retrieval 候选、过滤、fusion、evidence 模块与 internal/mcp 适配，逐步拆开 ask.go 的混合职责。

- embedding 缓存键包含内容哈希和模型版本；实现向量召回与真正生效的融合。
- 结构化证据包、授权过滤、重排、超时与降级。
- 上线 search / get 只读 MCP；用至少一个实际目标客户端验证初始化、工具发现、调用、授权和错误返回。

验收：与 BM25-only 在同一冻结问题集对照，改善语义改写问题且不破坏精确路径 / 错误码查询；无答案不会伪造答案；未授权数据不能进入模型上下文。

### P3：图遍历和时间协同

重建 graph 适配和投影契约；新增稳定 ID 映射、关系路径、as_of 与投影状态。

- 从确定性依赖、所有权、已确认变更做第一批关系，LLM 推断边受控纳入。
- 实现真正一 / 二跳遍历、方向与关系过滤，路径映射回 wiki 证据。
- 补 timeline / traverse MCP；实现历史有效期和迟到事件处理。

验收：真实 Graphiti / Neo4j 集成测试保留 invalid_at，明确完成事件使指定旧声明退出当前答案；含生产 / 测试分支的冲突不被误合并；图停机仍可搜 wiki，影响分析明确不完整。

### P4：维护闭环与受控进化

升级 evolve/crystal/reviews，增加 evidence support 检查、diff、影响分析、版本化摘要与回滚。

验收：错误 / 重复回答不能自我强化；每个自动失效有证据和审计；正式结论变更可批准、驳回和回滚；任务 / 审核跨重启保持。

### P5：生产运行与扩面

根据试点规模明确硬件、模型、并发和服务指标；增加限流、预算、告警、备份恢复、权限撤销传播与容量测试。PDF / RAGFlow 在有实际文档需求时独立验收后接入。

验收：完成原始证据 + wiki blob + 事务元数据的一致备份恢复演练；索引 / 图可从固定发布清单和保存的抽取结果重建。按实测扩容，不预先增加多个同类检索后端。

### 贯穿所有阶段的评测

建议先整理 60 个真实问题：定位 15、依赖影响 15、变更 / 故障时序 15、运行流程 10、无答案 / 冲突 5；权限对抗用例另外建立。每题标正确证据 ID / revision、必要路径、答案要点、时间环境和应拒答条件。调参集与冻结测试集分开，定期补充新问题。

以下为建议试点目标，不是已测性能或 SLA：

- 证据 Recall@10 >= 0.85；同时记录 nDCG@10、答案证据支持率和路径正确性。
- 冻结时序集中，将失效事实误报为现行的次数为 0；记录样本量，不能推成全量零错误。
- 权限对抗集中泄露为 0，测试包括搜索、页面、引用、图路径、缓存、摘要与晋升。
- 无答案题能明确缺证据；关键结论均可追溯，不以“包含正确关键词”作为通过。
- 检索 p95 暂定 <= 2 秒，单独测生成时延和成本；硬件、语料、并发确定后校准。
- 受支持的单次增量变更暂定 5 分钟内可查；分别观察 source lag、compile lag、search lag、graph lag。
- 人工评价要同时衡量维护成本：每周待审量、平均处理时间、重复知识率、每源编译 token / 费用。

## 11. 与现有规则的关系：哪些需要人审

本轮保留：wiki 主存、图投影、chunk 引用、单 enterprise、既有实体 / 边种类、解析失败不造页、正式变更人审、工单失效需审计、只降权不删、private 路径纪律。

以下仅作为拟议变更，必须经人审才能变成 schema / 正式行为：

1. 增加页面 / 声明版本、证据、ACL、环境和双时间字段及其校验规则。
2. 将 LWW 限定在草稿协作，正式发布用 base revision 比较，冲突保留双方完整快照。页锁继续默认五分钟，但不承担数据一致性的全部责任。
3. 将质量、证据支持度、新鲜度、热度与有效状态分开；明确 confidence=1 的语义，评估现行“质量 >= 0.7 自动 digest”的门控定义。
4. 单个 digest-latest 保留为兼容入口，同时新增历史修订；衍生摘要默认不算独立事实来源。
5. 若增加部署 / 符号等业务实体类型，另提 schema 变更；首版先以现有 File / Module / Change 及管理元数据承载，不先扩本体。

应把这些业务规则做成服务端可验证配置与流程；AGENTS.md 作为人和 Agent 的说明入口，不能单靠提示词承担权限、事务或发布约束。
