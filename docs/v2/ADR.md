## ADR-001：授权在检索热路径上的执行方式

### Status

Proposed

### Context

方案 §3 要求：BM25 与 kNN 都先做权限过滤；候选进入重排、模型和最终输出前再次核验当前授权；授权服务不可用时拒绝继续读取。

验收要求：10 万片段、10 路并发下本地检索部分 `p95 ≤ 2s`。

冲突在于：一次查询至少 3 次跨服务授权 RPC，其中输出前是逐候选核验；且 `auth` 不可用即全站拒绝读取，与方案为图设定的「降级并说明」不一致。

### Decision

采用 **物化授权 + 本地校验 + 版本失效**：

1. ES 每个片段存 `acl_subjects` + `acl_version` + `space_id`，BM25 与 kNN 均在查询内 `terms` 过滤，不访问 `auth`；
2. `auth` 只负责签发 ACL 版本与失效广播，把 `principal → {space_id, acl_version}` 快照写入 Valkey；
3. 重排前 / 输出前的核验改为**本地**比对快照版本号，版本号不匹配即丢弃该候选；
4. 降级规则：无快照 → fail-closed；有快照但 `auth` 不可达 → 继续服务并标记 `authorization_degraded`；图不可用同样降级并说明缺失能力。

### Consequences

**更容易**：达到 `p95 ≤ 2s`；消除 `auth` 成为全站单点；权限收紧通过版本号精确失效而非全量重算。

**更难**：ACL 版本的一致性成为新的正确性负担——撤权后广播失败会造成短暂的过度授权。需要：广播走 outbox + 重试、快照设 TTL 上限（强制回源）、并对 `authorization_degraded` 设置告警与审计留痕。

**要放弃**：「授权服务不可用即拒绝读取」的绝对表述。换来的可用性是有代价的——这是一个明确的**安全性 ↔ 可用性**取舍，若业务方要求绝对拒绝，需改回并接受 p95 不达标。

## ADR-002：Graphiti 分区策略

### Status

Proposed

### Context

方案 §3 要求按「知识空间 + 有效 ACL 域」分区，防止受限文档混入共享实体摘要。

但分区数 = 不同 ACL 组合数（文档级收紧会不断产生新域），会导致：同一实体在 N 个分区各存副本、跨分区同一性与合并规则缺失、泄漏面从「边」扩大到「节点副本」、权限收紧时需跨 N 分区原子重建。

### Decision

采用 **粗粒度分区 + 敏感内容不进图**：

1. `group_id = 知识空间`（不加 ACL 域）；
2. 受限文档**不参与图抽取**：图内只保留不含正文的占位节点 + 证据指针（`EvidenceRef`）；
3. 图节点/边必须映射回 wiki 声明与来源证据（继承方案要求）；
4. 敏感关系在遍历时按证据可见性过滤；
5. 图不可用 → 降级为纯 ES 检索，并在响应中说明缺失能力。

### Consequences

**更容易**：无副本、实体同一性天然成立；内容可见性只由 ES + 证据层负责，正确性的落点从一个面收敛到一个点；权限收紧只需失效边与占位节点；与「图是导航与时序投影」的定位一致。

**更难**：受限文档失去图导航能力（这是有意为之）；需要额外维护「占位节点 ↔ 证据」的映射。

**要放弃**：分区级硬隔离。这意味着**不能依赖 Graphiti SDK 的原生检索**（它不做 ACL 过滤），图遍历必须走自定义 Cypher。若坚持分区方案（选项 C），则必须额外实现分区注册表、跨分区实体 ID 映射表、分区重建原子切换三项，工期显著增加。

## ADR-003：工作流引擎的适用范围

### Status

Proposed

### Context

方案选定 Temporal 承载接入、编译、投影与后台维护工作流。平台共 12+ 个有状态组件，面向 100 名用户的内部场景。

方案对工作流的实际要求：按「来源版本 + 编译器版本」幂等执行；旧任务不能覆盖新结果；回滚生成新修订。

### Decision

1. **Temporal 只承载**：ingest 工作流、投影工作流、修订审核（长周期 human-in-the-loop）；
2. **查询路径绝不经过 Temporal**：检索、问答、图遍历、Agent 运行均为直接服务调用；
3. 幂等与防覆盖**不依赖 Temporal**——在 Postgres 中用
   `UNIQUE (source_id, source_version, compiler_version)` + lease + 心跳实现，
   使队列层即使被替换（如改为 PG 原生队列）也不影响正确性。

### Consequences

**更容易**：查询链路少一个关键依赖；幂等语义落在数据层，可测试、可替换；保留了 Temporal 在长周期审核与重试补偿上的真实价值。

**更难**：需要维护两套机制（Temporal 与 PG 任务表）的边界纪律，需在代码评审中明确「查询路径不得 import temporal」。

**要放弃**：用 Temporal 统一所有异步的整洁性。若未来证明 PG 队列已足够，可平滑移除 Temporal（因为正确性不在它身上）——这是这个决策最大的**可逆性**收益。

## ADR-004：事实可信度的计算方式

### Status

Proposed

### Context

09-08 评审判定 V1 存在 P0「无质量评估的自动结晶」：`internal/httpapi/server.go:50` 固定传 quality=0.9；`internal/crystal/crystal.go:22` 覆盖同一 digest 并设 `confidence=1`，摘要又被下一次搜索读到 → 自我强化回路。

方案 §1 要求废除该规则，但 §3 仍写「问答质量 ≥ 0.7 写 digest，并 `last_reinforced=now`、`confidence=1`」。

### Decision

1. `confidence` **只由证据支持度决定**：证据数量、来源权威性、是否有冲突、是否被 `supersedes`；
2. `last_reinforced` 只影响**排序新鲜度**，任何强化路径**不得写 confidence**；
3. 有效性、新鲜度、访问热度分别独立计算，互不折算；
4. 衰减任务按半衰期重复运行保持幂等（只降权不删）；
5. 同步删除 `AGENTS.md` 中「结晶 → confidence=1」的旧条款。

### Consequences

**更容易**：切断自我强化回路；使「可信度」可被审计（追溯到具体证据）；与方案「访问不提高事实可信度」一致。

**更难**：需要一个可解释的证据支持度函数——它必然是启发式的，需要随评测集迭代调参。

**要放弃**：「被反复检索的结论看起来更可信」这种直觉。这是刻意的：在本系统的语境里，流行度不是证据。

## ADR-005：代码基线的处置（已执行部分）

### Status

Accepted（部分执行）

### Context

经溯源确认 V2 实现从未开始（详见 `STATUS.md` §0），仓库 98.4% 文件为空壳，且 V1 与 V2 混仓导致构建互相干扰。

### Decision

1. 保留现有契约、编排、E2E、可观测性资产，不重写；
2. 空壳文件按阶段逐个填充，不批量删除结构（目录结构反映了服务划分，是有价值的设计产物）；
3. 立即清理伪产物 `knowledge-docker/.local/`、`services/python/.venv/`，并补齐 `.gitignore`（**已补齐**）；
4. 修复构建阻断项（**已修复** fixture 导致的 `go build ./...` 失败）；
5. V2 骨架跑通后，从工作树移除 V1 的 `internal/`、`cmd/`、`web/`。

### Consequences

保住了最有价值的资产（契约 1.2 MB、编排 31 KB、E2E 85 KB），同时避免「另起炉灶」造成的重复劳动。代价是仓库在过渡期同时存在两套 Go 代码，需要 CI 分别指定工作目录。
