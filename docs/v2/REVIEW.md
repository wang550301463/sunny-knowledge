# V2 方案架构评审（REVIEW）

> 评审对象：用户提交的《sunny-knowledge V2 重写方案》
> 评审基线：`a3533d5`　日期：2026-09-09
> 仓库现状类问题见 `STATUS.md`，本文聚焦**方案本身的架构风险**与一致性问题。

## 摘要

方案在知识建模上是成熟的：权威 wiki + 不可变修订 + 证据绑定 + 权限贯穿读路径，这套约束是对的，且明显吸收了 09-08 评审（见 `docs/reviews/2026-09-08-rd-knowledge-replan.md`）的 P0 结论。

但有 **3 个 P0** 会在实现中期集中爆发，且都不是编码细节，而是**执行点与建模选择**：

1. 授权检查放在热路径的跨服务 RPC 上，与 `p95 ≤ 2s` 直接冲突；
2. Graphiti 的 `空间 + ACL 域` 分区键会导致分区爆炸与实体重复；
3. 方案一边要废除 confidence 自我强化，一边又写了 `confidence=1`。

建议在动工前用 ADR 锁定这三项（见 `ADR.md`）。

## P0-1　授权的执行点与 p95 ≤ 2s 冲突

**方案原文（§3）**
> BM25 与 kNN 都先做权限过滤；候选进入重排、模型和最终输出前再次核验当前授权。授权服务不可用时拒绝继续读取。

**问题**
一次查询至少 3 次跨服务授权 RPC（召回前、重排前、输出前），其中「输出前核验」是逐候选核验。在 10 万片段 / 10 路并发下：

- 每次 RPC 5–20 ms × 数十候选 → 单次查询额外数百毫秒，`p95 ≤ 2s` 必然失守；
- `auth` 抖动 = **全站读不可用**。这与方案自己为图设定的「图不可用时降级并说明」不一致——同样是依赖故障，两种截然相反的处置。

**建议（方案内已埋好正确解法，只需把它推到底）**
方案已经设计了「ES 每条片段保存 ACL 主体、ACL 版本」——这就是物化授权。把它用足：

| 环节 | 机制 |
|---|---|
| ES 过滤 | `terms` 过滤 ACL 主体 + `acl_version`，纯本地，不查 auth |
| 重排/输出前 | 拿 Valkey 中 `principal → {space, acl_version}` 快照做**本地**比对 |
| auth 的职责 | 只做 ACL 版本的**签发**与失效广播，不参与每次查询 |
| 失效语义 | 版本号不匹配即拒绝（而非每次问 auth） |

**降级策略统一为一条**：

- 无任何快照 → **fail-closed**（拒绝，符合方案要求）；
- 有快照但 auth 不可达 → 继续服务，响应标记 `authorization_degraded`，并计入指标告警；
- 图不可用 → 同样降级返回并说明缺失能力（方案已如此规定）。

这样既保住「不越权」，又避免出现「一个组件抖动 = 平台不可用」的硬依赖。

## P0-2　Graphiti 分区键 `空间 + ACL 域` 会分区爆炸

**方案原文（§3）**
> Graphiti 按「知识空间 + 有效 ACL 域」分区，防止受限文档混入共享实体摘要。跨分区关联只能使用当前调用者同时可见、且有证据映射的关系。

**问题**
分区数 = **不同 ACL 组合的数量**，不是空间数。文档级收紧会持续产生新域，于是：

1. 同一 `Service` 实体会在 N 个分区各存一份副本，「跨分区关联」从例外变成常态，而方案没有定义跨分区实体的同一性判定与合并规则；
2. 泄漏面反而扩大：原方案想防的是「受限文档混入共享摘要」，但副本化后，**节点本身**也变成了需要保护的对象；
3. 权限收紧时要「立即阻断旧投影再异步重建」——在 N 副本模型下，重建要跨 N 个分区保证原子性，工程复杂度高。

**三个选项（权衡）**

| 选项 | 做法 | 得 | 失 |
|---|---|---|---|
| A | 单图 + 节点/边带 ACL 字段 + 自定义 Cypher 过滤 | 无副本、同一性天然成立 | 放弃 Graphiti SDK 原生检索，只能用其做写入与时序建模 |
| **B（建议）** | `group_id = 空间`（粗粒度）；**敏感文档不进图**，图内只留不含正文的占位节点 + 证据指针；敏感关系在查询时按证据可见性过滤 | 与方案「图是**导航与时序投影**」的定位一致；可见性收敛到 ES + 证据层，**只有一处需要正确** | 受限文档的图导航能力弱（但本来也不该暴露） |
| C | 维持 `空间 × ACL 域` | 隔离最彻底 | 必须补齐：分区注册表、跨分区实体 ID 映射表、分区重建的原子切换——三项都是新增复杂度 |

**建议 B**。理由：方案已把职责划清为「wiki 主存 / Graphiti 导航与时序 / RAGFlow chunk 逐字引用」，那么**内容可见性应当只由 ES + 证据层负责**，图只承载「谁依赖谁、何时变化」这类结构性信息。让一个组件同时负责导航和细粒度鉴权，是这类系统最常见的事故来源。

## P0-3　`confidence=1` 与「废除自我强化」自相矛盾

**方案原文（§1）**
> 同步更新项目规范，替换原来的单一图分组、正文 LWW 和**固定 confidence 自我强化规则**。

**方案原文（§3）**
> 摘要保存独立版本并追溯原始证据……问答质量 ≥ 0.7 写 `summaries/digest-latest.md`，并 `last_reinforced=now`、**confidence=1**。

**问题**
§3 的 `confidence=1` 正是 §1 要废除的东西：让系统的「被检索次数」决定「事实可信度」，就是 09-08 评审里被判定为 P0 的自我强化回路（`internal/crystal/crystal.go:22` 覆盖同一 digest 并设 confidence=1，摘要又被下一次搜索读到）。

**建议**

- `confidence` **只由证据支持度决定**，任何访问/强化路径都不得写它；
- `last_reinforced` 只影响**排序新鲜度**，不影响可信度；
- 衰减任务按半衰期重复运行保持幂等（方案已如此要求，正确）；
- 同步删除 `AGENTS.md` 中「结晶：…confidence=1」的旧条款，否则规范与实现再次分叉。

## P1-1　`Recall@10 ≥ 0.85` 无法归因，指标会失真

权限、有效状态、时间是**硬约束**（方案已明确，正确）。但硬过滤会吃掉召回，若不分层统计，指标失去诊断价值：

**必须在三个切点分别统计**：① 召回后；② 权限 + 时间过滤后；③ 重排后。
否则无法区分「检索能力差」与「过滤过严」，调优时会朝错误方向使力。

60 题标注集除答案外，还需标注两个维度：**是否有权限依赖**、**是否有时态依赖**，否则这两类问题（方案明确关注的重点）的失败原因无法定位。

## P1-2　Temporal 的复杂度与收益不匹配

方案引入的基础设施共 12+ 个有状态组件（Postgres / ES / Neo4j / Keycloak / Temporal / SeaweedFS / Valkey / OTel / Prometheus / Grafana / Graphiti / 11 服务）。对一个 100 用户的内部平台，这是很重的运维面。

方案对工作流的要求是「按来源版本和编译器版本幂等执行」「旧任务不能覆盖新结果」「回滚生成新修订」。前两条用 Postgres 任务表即可满足：

```sql
UNIQUE (source_id, source_version, compiler_version)  -- 幂等
-- 配合 lease + 心跳 + max(source_version) 防旧任务覆盖新结果
```

Temporal 真正不可替代的是**长周期 human-in-the-loop**（修订审核可能挂几天）与内置重试/补偿。

**建议**：Temporal 只承载 ingest / 投影 / 审核工作流，**查询路径绝不经过它**。这样既保留其价值，又不让查询链路依赖它的可用性。（详见 `ADR.md` ADR-003）

## P1-3　群聊泄漏的执行点必须在检索期

**方案原文（§4）** 已正确提出「提问者个人私有知识不能因群授权进入群回答」，并要求「最终输出前核验」。

**补充关键点**：流式输出一旦发出无法撤回，所以「群受众约束」必须是**检索阶段的硬过滤**（`audience=group` 参与 ES 过滤与图遍历过滤），生成后的复核只是兜底，不能作为主要防线。

同理，运行范围 `用户权限 ∩ Agent 范围 ∩ 本轮范围 ∩ 工具权限 ∩ 渠道群受众` 这个交集必须**在检索请求里一次性下推**，而不是在 Agent 侧逐工具计算——否则任一工具漏算即泄漏。

## P1-4　编译器缺陷的爆炸半径缺少熔断

方案允许「确定性的代码事实更新自动发布并审计」。但确定性 ≠ 正确：一个 Tree-sitter 查询写错，会在一次同步里改写全库。

**建议补三条熔断**：

1. 单次运行变更比例阈值（如 > 10% 页面变更）→ 自动转为人工审核；
2. 按语言 / 仓库分批发布，限制单次爆炸半径；
3. 自动发布必须可一键回滚，且**回滚生成新修订**（方案已有此要求，正确）。

## P1-5　新旧代码混仓，构建与 CI 会互相干扰

V1（`internal/` 2,483 行、`cmd/`、`web/`）与 V2（`services/`、`contracts/`、`knowledge-docker/`）同处一个仓库和一个根 Go 模块。已产生的实际后果：`services/python/tests/ingest/fixtures/monorepo/worker/service.go:5:2` 打断根模块 `go build ./...`（本次已修，见 STATUS §5）。

**建议**：V2 骨架跑通后，从工作树移除 `internal/`、`cmd/`、`web/`（V1 前端），保留于 Git 历史；V2 前端新建于 `web/` 或 `services/web/`。

## P2-1　ES Basic 的 ACL 过滤成本

每片段存完整 ACL 主体列表 → 收紧时该文档全量片段重索引，且 `terms` 数组膨胀。
建议存 `acl_version` + 解析后的主体集合，配合 `terms` 查询与请求缓存；收紧时按 `acl_version` 精确失效，避免全量重扫。

## P2-2　评测语料尚无标注

`evaluation/corpus.json` 自述 `preparing_unreviewed_cases`，只固定了仓库与 commit。方案要求 60 题人工标注，需从零建立，且应先于检索调优完成——否则 `Recall@10 ≥ 0.85` 无法测量。

## 值得肯定的设计（不要改动）

| 设计 | 为什么对 |
|---|---|
| wiki 为唯一写入口，chunk 只做逐字引用 | 切断了「chunk 静默覆盖正式结论」这条最常见的污染路径 |
| 证据必须绑定 `资源 + 知识修订 + 来源修订 + 精确位置 + 有效时间` | 使「引用可核验」成为结构约束而非提示词约束 |
| 发布必须比较 `base_revision`，正文/版本/审计/outbox 同事务 | 从根上消除并发修订的丢失更新 |
| 区分业务有效时间与系统获知时间；无部署证据不推断生产版本 | 直接命中 09-08 评审的核心缺口 |
| 推断关系单独标识，不自动成为正式结论 | 保住「事实 / 推断 / 缺口」的可区分性 |
| 修订工具只生成审核提案 | 把 Agent 的写能力限制在提案层，是正确的权限边界 |
| MCP 反馈需独立写 scope，不暴露改图/绕过审核的工具 | 外部入口与内部入口共用授权，避免了旁路 |
